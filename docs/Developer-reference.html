CopyCheck

Technical white paper | Implementation and developer documentation

Version 1.0 - 6 October 2026

CopyCheck reviews two public Solana wallets and explains how their observed execution results differ. It retrieves swap records through CoinGecko, identifies eligible closed positions in the same token, and decomposes the return gap into entry-price and exit-price effects.

Abstract

Copy trading does not guarantee identical outcomes. Two wallets can trade the same token but accumulate different average entry and exit prices. CopyCheck makes these differences inspectable: users enter two addresses and a UTC date range, read the comparison, and follow transaction evidence. The implementation uses deterministic arithmetic rather than an AI model to generate its findings.

The current product is a retrospective review tool. Its strongest claim is that a difference in observed average prices accounts mathematically for a difference in gross percentage returns. It cannot establish copy intent, diagnose the cause of an execution delay, or reconstruct a complete wallet ledger from swaps alone. Conservative eligibility rules withhold results when the supplied history cannot support them.

This paper describes the inspected source snapshot, its public website workflow, integration contracts, algorithms, operational limits and tests. It includes a saved live example and annotated excerpts. Proposed improvements are explicitly separated from implemented behavior.

1. Product purpose and practical use

A review after a trade, with evidence for the difference

A trader following another wallet wants to know whether their observed result matched the wallet they followed. CopyCheck answers a narrower, measurable question: for eligible positions in the returned swaps, how different were the two gross returns, and was the larger arithmetic contribution at entry or exit?

User questionCurrent answer
Did our outcomes differ?Compare percentage returns on eligible closed token positions.
Where did the difference appear?Separate the entry-price effect from the exit-price effect.
Did I enter later?Show the first-buy timestamp difference; this is an observation, not a diagnosis.
What supports the result?Inspect normalized fills, USD values, timestamps and explorer links.
How many dollars did I lose?Not a current output. The headline is a return difference in percentage points, before fees.
Did my bot malfunction?Not established. Bot logs, quotes and transaction submission evidence are not collected.

How someone could use it

After both positions have closed, the user compares their address with the address they intended to follow. If the result repeatedly shows a worse exit price, they have a reason to inspect exit settings or execution records. If history is incomplete, they can shorten the range and inspect the evidence rather than relying on an unsupported percentage. This is a starting point for investigation; it does not select profitable wallets or prescribe a trade.

What is implemented

The app supports Solana, two addresses per request, an inclusive range of up to 30 UTC calendar days, one observed position per token, price comparisons, evidence links and JSON export. A synthetic example is available without credentials. Live data comes from a server-side CoinGecko integration.

What is outside the current product

There is no trade execution, wallet signing, token custody, automated copy bot, predictive signal, complete portfolio return, fee-adjusted P&L or confirmed copy-relationship detector. The earlier pool-flow monitoring screens are a different prototype and are not the algorithm documented here. No claim of market uniqueness or demonstrated customer demand follows from this implementation.

2. Website workflow

From two addresses to a review the user can inspect

On initial load, the page shows a clearly marked synthetic example. The wallet fields are blank and the dates default to the last seven UTC calendar days. The page asks the server whether an API key is configured. Users can return to the example through Try an example.

StepWebsite behavior
1. Enter addressesWallet you followed becomes the leader input; Your wallet becomes the follower input. Both are public addresses, not authentication credentials.
2. Select datesThe requested dates use UTC. Today ends at the request time rather than at a future midnight.
3. Compare walletsClient validation runs, controls lock during the request, and JSON is sent to /api/compare.
4. Read the summaryLeader and follower mean returns and their percentage-point difference use only comparable token rows.
5. Open a tokenThe detail panel explains the finding and shows average prices. The Evidence tab exposes supporting fills.

Reading the result correctly

A negative gap means the follower return is lower. It does not mean the follower necessarily lost money: a follower at +8% and a leader at +10% have a -2 percentage-point gap. A row can be visible yet excluded from the headline; its finding explains why. An empty comparable set produces unavailable values rather than a fabricated zero.

Failure behavior

If a new comparison fails, the previous review remains visible with an error explaining that it is the previous result. This prevents a failed fetch from silently replacing a valid review. The browser has a 35-second request timeout; the server data request budget is 25 seconds. A ref-based lock prevents overlapping comparisons in the same page instance.

The status route checks only whether the key exists. Consequently the current Live data connected label is not evidence of a successful provider request, plan entitlement or fresh data. A successful comparison is stronger evidence. A failed status fetch can leave the initial checking state visible.

4. Input validation and time boundaries

Reject malformed requests before requesting market data

const alphabet =
  "123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz";
let n = 0n;
for (const c of v) n = n * 58n + BigInt(alphabet.indexOf(c));
let bytes = 0;
while (n > 0) { bytes++; n >>= 8n; }
return bytes + (v.match(/^1*/)?.[0].length || 0) === 32;

lib/coingecko.ts, validAddress; excerpt reformatted after its type/regex guard.

The initial guard accepts only a 32-44 character base58 string. This excerpt then decodes its numeric value using BigInt. Leading 1 characters represent zero bytes and are added back to the byte count. Exactly 32 decoded bytes are required. This is structural validation, not proof that an address exists, belongs to the user, or is controlled by a particular trader. Identical leader and follower strings are rejected.

const start = Date.parse(from);
const end = Date.parse(to) + 86400000 - 1000;
if (end < start || end - start >= 30 * 86400000)
  throw new Error("Choose an ordered date range of no more than 30 days.");
// Other guards reject invalid calendar dates and future dates.
return { leader: b.leader, follower: b.follower,
         from, to, start, end: Math.min(end, now) };

lib/coingecko.ts, validateRequest; shortened excerpt, with intervening guards noted.

Dates must match YYYY-MM-DD and survive an ISO round trip, which rejects impossible calendar dates. Date-only parsing establishes UTC midnight. Adding a day and subtracting one second makes a past end date inclusive through 23:59:59. A 30-day inclusive span is accepted; a 31-day span is not. Future dates are rejected and today is capped at now.

Units and reproducibility

JavaScript uses milliseconds internally. The provider query uses whole UNIX seconds, obtained by flooring start/1000 and end/1000. Normalized trades return to milliseconds through Date.parse. A regression test protects this conversion because a full ISO string with milliseconds previously caused a provider rejection.

The exported report preserves date strings and createdAt, but not the exact capped fetch end, provider cursor chain or raw responses. A same-day query made later can return additional fills. Reproducing a saved report means recalculating from its saved normalized trades, not expecting a fresh API request to be identical.

The page cap is an application safety bound, not a provider guarantee that 1,500 records cover the period. complete means the returned page sequence ended under these rules. It cannot establish that every venue, transfer, token event or historical holding is represented. A longer cursor cycle eventually reaches the page cap.

Errors and availability

Provider 401/403 errors produce an access/plan message; 429 produces a rate-limit message. Other HTTP failures produce a generic provider error. The route maps these failures to HTTP 502. There are no automatic retries, exponential backoff or application result cache. Both fetches share a 25-second timeout; a rejected promise does not explicitly cancel its sibling immediately.

Precision and identity

Quantities and USD values are JavaScript numbers, using IEEE-754 binary floating point. The program does not retain integer base units or arbitrary-precision decimal arithmetic. A relative quantity tolerance is used when deciding whether inventory has closed. Display rounding occurs after analysis and should not be used to reproduce exact calculations.

Token addresses remain case-sensitive. Trade IDs, not transaction hashes alone, are deduplication keys because a transaction may contain multiple swap records. Live labels are abbreviated token addresses; the adapter does not fetch token names. Pool and DEX metadata, provider price fields and raw response bodies are not retained in Trade. The export is therefore an analysis snapshot rather than a raw provider archive.

7. Reconstructing observed positions

One token, one observed round trip, conservative exclusions

positions() removes duplicate IDs and invalid numeric records, groups by exact token address, and sorts each group by time then ID. It accumulates inventory from observed buys and sells. Starting inventory is assumed to be zero for this reconstruction; negative inventory flags an unknown cost basis rather than inventing missing purchases.

const tolerance = Math.max(bought, sold) * 1e-7;
let inventory = 0, cycles = 0, unknown = false, active = false;
// Inside the sorted-fill loop:
if (t.side === "buy") {
  if (!active) { cycles++; active = true; }
  inventory += t.quantity;
} else {
  inventory -= t.quantity;
  if (inventory < -tolerance) unknown = true;
  if (Math.abs(inventory) <= tolerance) {
    inventory = 0; active = false;
  }
}

lib/analysis.ts, positions; excerpt omits the timestamp-side check described below.

The tolerance is 0.00001% of the larger total quantity. Returning within that tolerance of zero closes the active inventory cycle. A new buy after closure starts another cycle. The code separately tracks sides at identical timestamps; opposing fills sharing a timestamp mark ordering as uncertain even though ID sorting provides a deterministic display order.

Status, in priority orderCondition and consequence
unknownNegative observed inventory, no buys, or opposing fills at the same timestamp. No return.
multipleMore than one observed inventory cycle. No combined return.
closedBought and sold totals agree within tolerance. A gross return may be computed.
partialSome sells, but observed bought quantity remains. No full-position return.
openObserved buys without a completed exit. No full-position return.

The algorithm permits multiple buys and sells within a single active cycle. It does not implement tax lots, FIFO/LIFO or matching several separate round trips. remaining is max(0, bought - sold) in the returned records, not the actual on-chain balance. Transfers, starting holdings and untracked venues can invalidate a ledger interpretation even when the observed totals balance.

8. Matching and eligibility

A candidate relationship with explicit gates

const complete = leaderHistory.complete && followerHistory.complete
  && !leaderHistory.skipped && !followerHistory.skipped;
const entryDelay = l?.firstBuy != null && f?.firstBuy != null
  ? (f.firstBuy - l.firstBuy) / 1000 : null;
const plausible = entryDelay !== null
  && entryDelay >= 0 && entryDelay <= 1800;
const comparable = complete && plausible
  && l?.returnPct != null && f?.returnPct != null;

lib/analysis.ts, compare; exact conditions with expanded formatting.

The row set is the union of both wallets' token addresses. Eligibility requires the same exact token, both reliable closed-position returns, and a follower first buy between zero and 1,800 seconds after the leader first buy. This 30-minute horizon is a fixed heuristic in this version. There is no statistical confidence model, bot relationship lookup or proof of copy intent.

The global coverage gate

If either history is truncated or either wallet has even one skipped record, all token comparisons are suppressed. This is intentionally conservative: the application cannot assign an unusable record safely to a particular position. It also means one malformed record can hide an otherwise useful pair. Narrowing the dates can help, but does not repair provider coverage.

FindingInterpretation
Incomplete historyThe global coverage gate failed.
No follower record / Follower onlyThe token was observed in just one supplied history.
Unknown cost basisInventory or timestamp ordering cannot support a return.

These checks are evaluated in the order shown. A coverage failure can therefore take precedence over a missing-wallet finding. A match can be coincidental; a genuine copy outside the horizon can be excluded. The rule is an auditable filter, not a discovered causal relationship. Exit delay is reported but is not an eligibility threshold.

9. Return and attribution mathematics

Exactly what the headline and explanation measure

For a token, let B be total bought quantity, S total sold quantity, Ubuy the sum of buy USD volumes and Usell the sum of sell USD volumes. Average entry E = Ubuy / B and average exit X = Usell / S. These are quantity-weighted average fill prices, not averages of displayed prices. For an eligible closed position, R = 100 * (X / E - 1).

entryEffect = (l.exit / f.entry - l.exit / l.entry) * 100;
exitEffect  = (f.exit / f.entry - l.exit / f.entry) * 100;
gap = f.returnPct - l.returnPct;

lib/analysis.ts, compare; source formulas, with non-null assertion omitted for readability.

Use EL and XL for the leader prices, EF and XF for the follower prices. Entry effect changes the entry from EL to EF while holding XL fixed. Exit effect then changes the exit from XL to XF while holding EF fixed. Adding the effects cancels XL/EF, leaving 100 * (XF/EF - XL/EL), exactly the follower return minus the leader return apart from floating-point rounding.

Why this is an attribution convention

This is an entry-first counterfactual decomposition. A different order of substitution can allocate the components differently while preserving the same total gap. It does not show that either wallet could have obtained the other's fill, nor identify whether market movement, slippage, routing, fees or a bot setting caused a price difference.

The larger absolute component selects the explanation; ties select exit. A gap with absolute value below 0.05 percentage points is labeled Similar execution. The phrase essentially the same average entry price uses a separate 0.05% relative entry-price threshold. These are display heuristics, not significance tests.

Aggregation and units

For N comparable token rows, the headline leader return is sum(RL)/N, and the follower return is sum(RF)/N. Every eligible token has equal weight regardless of trade size. Headline gap is the difference of these means. A percentage point is an arithmetic difference between percentages: -3.2% minus -2.4% is -0.8 pp. This is not a portfolio return, a dollar loss or a fee-adjusted result.

Gas, priority fees, tips and platform fees are not explicitly ingested or deducted. The app uses the provider's USD trade values as supplied. Changes in trade size alone do not change the price-based return when mean prices remain the same, although real dollar exposure changes.

Production hardening priorities

The published interface is public. An attacker can call its server endpoint repeatedly and consume the owner's provider allowance. The same-origin comparison reduces some unwanted browser calls but arbitrary clients can supply an Origin header. Add server-enforced rate limits, usage budgets and monitoring before treating the service as ready for unrestricted traffic. Key rotation and provider account restrictions belong in the operational process.

A stronger version would enforce byte limits while streaming, validate output shape at the client boundary, distinguish provider rate limiting in HTTP status, and record exact fetch cutoffs. These are recommendations, not features already implemented. Do not claim that the page's busy state prevents concurrent requests from other tabs or clients.

Scientific and financial limits

Data completeness is conditional on provider coverage. USD valuations are provider-supplied, numbers use floating-point arithmetic, and fees/transfers/prior holdings are outside the model. A price decomposition is not causal evidence. There is no claim of audited accuracy, profitability, execution improvement, or suitability for tax reporting. These boundaries determine what evidence is needed before expanding the product's claims.
